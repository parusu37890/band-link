# Band Link 開発・エージェント運用

状態: 実装中の運用設計。採用技術・役割・4つのエンジニアリング方式は要件定義書第13章で確定。下記の具体的な受け渡し手順は運用ルールであり、CIやGitHubの設定が完了したことを意味しない。

詳細な方式と依頼テンプレートは `docs/engineering-method.md` を参照する。

## 役割と出力

| 役割 | 責任 | 完了時に返す情報 |
|---|---|---|
| 進行・設計 | 要件照合、作業分割、担当範囲の指定、結果の統合 | 対象要件、設計判断、残課題、次の作業 |
| 実装 | 指定範囲の変更、JUnitの作成と実行 | 差分、理由、実行した検証、未検証事項 |
| コードレビュー | 実装担当とは独立して要件・設計・権限・不具合を点検 | 重要度、ファイル位置、発生条件、影響、修正案 |
| 検証 | JUnit結果の確認、Playwright MCPによるST、必要なログ確認 | 対象リビジョン、環境、手順、期待結果、実結果、証跡 |

レビュー係は原則としてコードを変更しない。修正は実装係へ返す。担当名を分けるだけで独立レビュー済みとは扱わない。

## 作業依頼に含める情報

目的、対象要件の章、読む資料、対象ブランチ・リビジョン、編集可能なファイル、他担当と共有する契約、受け入れ条件、実行する検証、今回扱わない範囲を記す。

並行実装する場合は別ブランチ・別worktreeを使う案とする。同じファイルの同時編集を避ける。DBスキーマや共通APIなどの共有部分は先に進行・設計係が調整する。

## PRの流れ

`feature/<name>`で作業し、対象要件と受け入れ条件をPRへ記載する。実装係がJUnitを実行し、レビュー係・検証係が同じ差分を確認する。重要な指摘は修正後に再確認する。差分が変わった場合は影響のある検証を更新する。

推奨するマージ条件は、CI成功、独立レビュー完了、必要なST成功、重大な未解決指摘なし、関連文書更新済み。必須チェック名・ブランチ保護・マージ方式・操作担当は設定前に確定する。

## テストとログの検証

- JUnitでは時刻を制御できる設計にして12時間・30日の境界を検証する。待ち時間を実際に経過させるテストにしない。
- 結合テストでは1人1公開投稿と1組1会話の並行処理を検証する案。DB方式は未決。
- Playwright MCPの接続を確認してからSTを実行する。利用できない場合は未実行と報告し、他のツールの結果を同じものと称しない。
- STは2人以上のテストアカウントと管理者を使い、権限の違い・ブロック・通報・利用停止を確認する。
- ログはリクエストIDで検索できること、私的な本文や認証情報が含まれないことを確認する。
- ローカル用のメール受信確認手段、DB、画像領域は既存アプリから分離する。

## 文書の責任範囲

`requirements.md`は何を作るか、`DESIGN.md`は見た目の統合方針、本書は作業の進め方を扱う。DB/APIは`docs/db-api-design.md`、ログ基盤は`docs/infra-design.md`で扱う。設計判断は今後 `docs/decisions/` に、テスト証跡は今後 `docs/test-results/` に蓄積する案。

AIへの引き継ぎには、決定事項、対象リビジョン、完了した検証、未決事項、直近の失敗と次の行動を残す。ツールが利用可能なことと、そのツールを使って検証済みであることを区別する。
