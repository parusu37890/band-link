# Band Link エンジニアリング方式

Band Linkでは、AIを使った開発を一度の生成で終わらせず、資料・検証・修正を繰り返して品質を上げる。以下の4方式を組み合わせる。

## プロンプトエンジニアリング

担当エージェントへの依頼を、次の順で書く。

1. 目的と利用者への効果
2. 対象要件・設計書・変更可能な範囲
3. 守る制約（権限、セキュリティ、既存契約、禁止事項）
4. 受け入れ条件と実行する検証
5. 出力形式（差分、判断理由、テスト結果、残課題）

「実装して」だけの依頼を完了条件にしない。確定事項・提案・未決事項を依頼文内で分ける。レビュー依頼には実装者の説明を鵜呑みにせず、要件から独立して確認するよう明記する。

## コンテキストエンジニアリング

会話の記憶に依存せず、必要な情報を次のファイルへ保存する。

- `requirements.md`: 作る機能と確定仕様
- `docs/db-api-design.md`: DB、API、権限、状態遷移
- `docs/infra-design.md`: ログ基盤とローカルインフラ
- `DESIGN.md` と `docs/design-references/`: UIの方針と原文
- `docs/decisions/`: 判断理由と影響
- `docs/HARNESS.md`: 実行確認済みのコマンド
- `docs/test-results/`: STや検証の証跡（作成時に対象リビジョンを記録）

エージェントは作業開始時に対象資料を読み、終了時に要件・設計・検証結果の差分を更新する。資料にない推測を確定仕様として書かない。

## ハーネスエンジニアリング

AIが変更後に自分で確認できるよう、ローカル起動、DB、メール確認、テストデータ、JUnit、Playwright MCP、ログ検索を再現可能にする。成功したコマンドだけをハーネス文書へ記録し、未検証の操作は明示する。機密情報は環境変数で渡す。

## ループエンジニアリング

機能を小さな単位に分け、1ループで検証できる範囲だけを扱う。大きな機能を一度に実装して最後にまとめて確認しない。

```text
要件を1つ選ぶ
  ↓
設計・受け入れ条件・担当を固定
  ↓
実装
  ↓
JUnitで単体検証
  ↓
独立コードレビュー
  ↓
Playwright MCPでST
  ↓
Elasticsearch/Kibanaで処理とエラーを確認
  ↓
指摘を修正し、影響する検証を再実行
  └── 未達なら同じループを続ける
```

### ループの状態

| 状態 | 入る条件 | 必須の出力 | 次へ進む条件 |
|---|---|---|---|
| READY | 対象要件が1つに絞られている | 目的、対象ファイル、受け入れ条件、担当 | 受け入れ条件が検証可能 |
| DESIGNED | DB/API/UIの契約と権限が決まっている | 設計差分、判断理由、テスト観点 | 実装者とレビュー者が契約を共有 |
| IMPLEMENTED | 実装と必要なJUnitが完了 | 差分、変更理由、未実装範囲 | コンパイルと対象JUnitが成功 |
| REVIEWED | 実装者と別の担当が確認した | 指摘一覧、重要度、対象位置 | 重大指摘が解消または明示的に保留 |
| ST_VERIFIED | Playwright MCPで業務操作を確認した | 手順、期待結果、実結果、証跡 | 受け入れ条件をブラウザで満たす |
| OBSERVED | 関連ログを確認した | request_id、エラー、機密情報の確認 | ログ追跡と安全性を確認 |
| DONE | 必須検証がすべて記録済み | 完了判定、対象リビジョン、残課題 | PRレビュー・マージ候補になる |

### 失敗時の戻り先

- 受け入れ条件が曖昧なら `READY` に戻す。
- DB/APIの契約が原因なら `DESIGNED` に戻し、実装前に設計を更新する。
- コンパイル・JUnit失敗なら `IMPLEMENTED` に戻す。
- 要件漏れ・権限・セキュリティ指摘なら、実装者へ返し `IMPLEMENTED` に戻す。設計変更が必要な場合は `DESIGNED` に戻す。
- ST失敗なら、再現手順を保存して `IMPLEMENTED` に戻す。画面仕様の誤りなら `DESIGNED` に戻す。
- ログが追跡できない、または機密情報が出た場合は `IMPLEMENTED` に戻し、ログ契約を修正して再検証する。

失敗時は「対象リビジョン・再現条件・期待結果・実結果・原因仮説・確定原因・修正・再検証結果」を記録する。単に「修正済み」と書いてループを閉じない。

### ループの境界

- 1ループは、通常1つのユースケースまたは1つの業務ルールに限定する。例: 「メール未確認ユーザーは投稿できない」「1ユーザー1公開投稿」のように分ける。
- 複数の担当が同じファイルを編集しない。共有契約を先に設計し、実装・レビュー・検証の担当を分ける。
- ループ中に別の要件が見つかったら、現在の範囲へ混ぜず、別のループ候補として記録する。ただしセキュリティやデータ破壊につながる問題は現在のループを止めて先に処理する。
- 3回同じ失敗を繰り返した場合は、実装を続けず、失敗記録と必要な判断を進行・設計係へ返す。
- ループ完了後にPRへ、対象要件、受け入れ条件、検証結果、残課題、次のループを記載する。

### ループの品質指標

完了数だけを評価しない。各ループで、受け入れ条件の充足率、JUnit/STの実行結果、重大指摘の数、再現可能な証跡の有無を記録する。未実行の検証は成功として数えない。

### 依頼・完了記録テンプレート

担当エージェントへは次の形式で依頼する。

```text
目的:
対象要件:
読む資料:
変更可能な範囲:
守る制約:
受け入れ条件:
実行する検証:
返す内容: 差分 / 判断理由 / テスト結果 / 未達・残課題 / 次の戻り先
```

ループ完了時は次を記録する。

```text
ループID:
対象リビジョン:
受け入れ条件ごとの結果:
JUnit:
レビュー:
ST:
ログ確認:
失敗と修正:
残課題:
次のループ:
```

## エージェント間の契約

進行・設計係は各ループの対象と完了条件を定義する。実装係は変更とJUnit結果を返す。レビュー係は原則変更せず、重要度・場所・影響・修正案を返す。検証係は対象リビジョンと実際の操作結果を返す。次の担当は前担当の説明ではなく、共有資料と成果物を基準に判断する。
