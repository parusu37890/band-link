# 競合レビューを踏まえた再設計と、未着手フローの検証

日付：2026-09-06。ブランチ：`main`（直接push運用）。前回記録：`2026-09-06-real-data.md`。

## 参照した競合

`https://oursounds.net/` — バンドメンバー募集の掲示板。2005年から運営。利用者視点とデザイナー視点の両方で確認した。

**採り入れた点**

- 一覧に投稿からの経過日数が出ている。募集は鮮度で読む価値が決まるため、この情報が無いと半年前の投稿と今日の投稿が同じ見た目になる。
- 投稿者の**最終ログイン**を出している。見知らぬ相手に書くかどうかは「まだ読んでいる人か」で決まるので、この分野で最も効く信頼情報。ただし本サービスは正確な日時ではなく区分（3日以内／1週間以内／1か月以内）にした。判断に必要なのは「返信が来そうか」だけで、ログイン履歴そのものを公開する必要はないため。古い場合と不明な場合はどちらも非表示とし、特定のアカウントを目立たせない。
- 一覧の各行からメッセージ・プロフィールへ直接行ける。本サービスは一覧→詳細→サイドバーの3手だった。
- トップで「何のサイトか」「いつから」「何にこだわっているか」を最初に言い切っている。

**採らなかった点**

- 広告が本文を覆う（モーダル広告・バナー多数）。信頼性と集中を損なう。
- 「指定なし」の空欄が並ぶ。本サービスも同じ問題を「未設定」で抱えていたため、埋まっている項目だけ出す方式に変更した。
- 本文が改行だけの塊で、情報の優先順位が付いていない。

## 変更点（詳細は`DESIGN.md`とコミット）

- 一覧カード：装飾の通し番号「No. 0001」を投稿からの経過時間に置換。投稿者に活動区分を表示。メッセージ導線をカードへ。
- トップ：抽象コピー「一緒に鳴らす、仲間を探そう。」を、掲示板であること・現在の掲載件数・登録なしで閲覧できることを述べる文に変更。装飾的な英語ラベル「JAPAN / BAND LINK」を削除。ページタイトルとmeta descriptionも同様。
- プロフィール：未入力項目を並べず、埋まっている項目だけ表示。全て未入力なら1行で伝える。
- 「掲載順」→「新しい順」。

## 検証で見つけて直した不具合

1. **ブロックが一覧に効いていなかった**。requirements 8章の「ログイン中の募集一覧では双方に相手の投稿を表示しない」に対し、`/api/posts`と`/api/posts/page`がブロックを参照していなかった。修正後、投稿10件を持つ相手をブロックすると41件→31件になり、詳細URLは200のまま（[[0004]]どおり）。
2. **ブロックを作る導線がUIに存在しなかった**。設定画面は一覧と解除だけを持ち、作成手段がどこにも無いため機能が到達不能だった。公開プロフィールに追加。
3. **投稿画像は保存後に管理できなかった**。API側は削除・並べ替えを実装済みだったが、UIが無かった。編集画面に追加。
4. **通報の内容が運営に見えなかった**。requirements 8章が求める「通報された本文・画像」を保存も表示もしていなかった。通報時にスナップショットを取得し、管理画面に表示。会話画像は参加者限定のため、**通報対象の画像に限りADMINへ開放**した。参加者でない管理者（会話0件）が200、通報されていない画像は404、一般ユーザーの第三者は403のままであることを確認。

## 大量データでの表示（追加検証）

通知41件・会話64件を投入して確認した。

- 通知：41件すべて描画、未読の罫線表示とヘッダーの未読ドットは正しい。横はみ出しなし。**ページングは無く全件を返す**ため、件数が増え続けると1ページが伸び続ける（7,689px）。件数上限や追加読み込みは要件に無いので実装していないが、運用で増えた場合の課題として残す。

## 追記：メッセージ画面が空表示になる不具合（2026-09-06）

### 1. `/api/messages/conversations` が500（ローカルのみ・アプリの不具合ではない）

メッセージ画面が0件になったため調査。`logs/band-link.ecs.json` に例外が残っていた。

```
java.lang.ClassNotFoundException: com.example.bandlink.dto.PeerResponse$1
	at com.example.bandlink.dto.PeerResponse.from(PeerResponse.java:13)
	at com.example.bandlink.dto.ConversationResponse.from(ConversationResponse.java:9)
	at com.example.bandlink.controller.MessageController.conversations(MessageController.java:26)
```

`PeerResponse$1` は enum の`switch`式に対してjavacが生成する合成クラス。増分ビルドが
`PeerResponse.class` だけを更新し、合成クラスを`target/classes`へ書き出さなかった。
ソースは正しく、同じコミットのCIは成功している（run 34016118457）。`clean`付きの再ビルドで解消。
手順は [docs/HARNESS.md](../HARNESS.md) に記録した。

再ビルド後の確認：`GET /api/messages/conversations` → 200。退会済みの相手（id 25）は
`username: "退会済みユーザー"` / `profileImageUrl: null` を返し、docs/decisions/0001 の状態ラベル規則どおり。
`GET /api/messages/conversation/1` → 200、`/conversation/2` → 200。

### 2. 非表示タブで開くと「まだ会話がありません」と表示される（実装の不具合・修正済み）

500を直した後も画面は0件のままだった。原因は`community.js`の`refresh()`冒頭にあった
`document.hidden`ガードで、**初回ロードごと**スキップしていた。データを一度も取りに行かないまま、
「まだ会話がありません」「募集から相手を探す」という*事実と異なる*空状態を描画していた。

ポーリングの抑制は`ui.js`の`poll()`が既に`document.hidden`で行っており、
`refresh()`側の同じ判定は重複していた。重複分を削除し、初回ロードとユーザー操作
（送信後の再取得・「最新のメッセージ」・再試行ボタン）は可視状態に関わらず走るようにした。
未読を自動で既読にする判定（`!document.hidden`）は意図どおりなので残している。

修正後、`document.hidden === true` のまま検証：

| 画面 | 結果 |
|---|---|
| `/messages/1` | 会話2件、メッセージ30件、ヘッダ「ミッドナイト・コード」、空状態なし |
| `/notifications` | 通知15件、「15 / 41件を表示」、段階表示は従来どおり |

バックグラウンドで復元されたタブや、リンクを新規タブで開いた場合に該当する。
`poll()`の`visibilitychange`で最終的には回復していたが、それまで誤った空状態を見せていた。

### 検証時の注意（ツール側の制約）

Browserペインは長いページをスクロールした後の再描画に失敗し、スクリーンショットが真っ黒になる。
`document.elementFromPoint` では正しい要素が返り、固定オーバーレイも存在しないため、アプリ側の
描画不具合ではない。スクロール位置での見た目を確認する場合は、先行要素を一時的に隠して
スクロールせずに撮る必要がある。Playwright MCPのクリック不発と同じく、ツール側の制約として記録する。

### 4. ヘルプに書いたブロックの説明が実装と食い違っていた（修正済み）

作り直したヘルプの初稿に「その相手の募集は一覧に出なくなり」と書いたが、これは片方向しか
表していなかった。既存のブロック確認ダイアログは「お互いの募集が一覧に表示されなくなり」と
書いており、同じ製品の中で2つの説明が矛盾していた。

`PostService.blockedCounterparts` は `findByBlockerIdOrBlockedId(viewerId, viewerId)` を使い、
ブロックの向きに関わらず相手側のIDを返す。既存文言のほうが正しい。実測でも確認した。

| 状態 | demo01に見える投稿者 | demo02に見える投稿者 |
|---|---|---|
| ブロック前 | 1・2・3（各10件） | 1・2・3（各10件） |
| demo01がuser2をブロック | 1・3 | 2・3 |

ブロックした側だけでなく、**された側からもブロックした人の募集が消える**。ヘルプの文言を
実装に合わせ、過去の会話が残ることと、ログアウトすれば公開情報は見られること
（requirements 116）を併記した。検証後にブロックは解除し、デモデータの状態を戻している。

### 何に高さを使っていたか

1行は3ブロックが縦に積まれ、そのうち本文抜粋が2行(約50px)、投稿者ブロックがアバター＋名前＋
活動区分＋メッセージボタンで60pxを占めていた。ヘッダー側は見出しの説明文と掲載ボタンで148px、
キーワード欄のラベルが1行(21px)、検索欄と「条件を絞る」が別々の行、案内文が約40px。

### 変更内容（`@media(max-width:640px)`のみ。PCは未変更）

- 本文抜粋・ジャンルチップ・行内の連絡ボタンを一覧から外した。いずれも詳細画面に1タップで届く。
  一覧で残したのは、タップするか決める材料——パート・地域・活動頻度・投稿の鮮度・投稿者の活動区分。
- 3ブロックの縦積みをやめ、種別・鮮度と投稿者を1行目に同居させた（どちらも短く、幅が余っていた）。
  2行目がタイトル、3行目が募集パートと条件。
- 検索欄と「条件を絞る」を1行に。キーワードのラベルは入力欄のプレースホルダが兼ねるため視覚的に隠した
  （`clip-path`でスクリーンリーダーには残す）。見出しの説明文と案内文はスマホでは出さない。

### 2. 検索ボタンの黒背景とズレ

`class="button primary"` だったため `background: var(--ink)` の黒い四角が入力欄の中に載っていた。

### 3. ページ遷移（原因は想定と違った）

APIは速かった（1リクエスト4〜18ms）。遅さの原因は**リンククリックを一切横取りしていなかった**こと。

`navigate` は `location.assign` で、クリックのたびに完全な再読込。シェルはCSS 8本・JSモジュール7本を
読むので、1クリックごとにそれを全部捨てて取り直し、間に白い瞬きが入っていた。ルーター（`route`）は
最初から存在していて、クリックを渡す人がいなかっただけ。

同一オリジンかつシェルが持つ経路へのリンクを `pushState` + `route()` に流すようにした。
それ以外（`/api`、アップロード、ダウンロード、別タブ指定、修飾キー付きクリック）はブラウザに任せる。
`navigate` も同じ経路にした。

| | 変更前 | 今回 |
|---|---|---|
| 遷移時の再読込 | ドキュメント全体 | なし |
| CSS/JSの再取得 | 15ファイル | **0** |
| 最初のDOM更新まで | 全読込 約46ms（ローカル） | **20ms** |

## 追記：確認メールが送られていなかった（2026-09-07）

指摘「確認トークンがメールに届かない」「トークンを送らなくても普通にログインできるのはまずい」。

### 事実確認

**未確認でログインできるのは仕様どおり。** requirements 45「投稿とメッセージ送信にはログイン
およびメールアドレス確認が必要」で、ログイン自体は確認を要求していない。実測でも要件が求める
ゲートは効いていた。

| 未確認アカウントの操作 | 結果 |
|---|---|
| ログイン | 可（仕様どおり） |
| 募集の投稿 | **409 RULE_VIOLATION「メールアドレスの確認が必要です」** |
| メッセージ送信 | **409 RULE_VIOLATION** |
| 閲覧 | 可 |

**メールが届かないのは要件未達。** requirements 107「認証・復旧用メールは提供する」に対して、
送信のコードもライブラリも存在しなかった。トークンはDBに作られるだけで誰にも伝わらない。
つまり利用者は自力では確認も再設定も終えられず、投稿・送信に永久に到達できなかった。

### 実装

`MailService` を追加し、登録時とパスワード再設定要求時に送る。

- **未設定なら送らない。** `MAIL_HOST` か `MAIL_FROM` が空なら警告を1行残すだけで、
  登録・再設定そのものは通す。送信失敗も同じ扱い。相手のメールサーバの都合で
  アカウントが作れなくなるほうが困る。
- **トークンはログに書かない**（requirements 13.3）。警告文にも含めない。
- SMTPの資格情報は環境変数から受け取り、リポジトリには置かない。

### 検証（受信まで確認した）

配信サービスは未決（requirements 11章）なので、受信するだけの簡易SMTPサーバ
（`scripts/dev/smtp-stub.js`）を立てて経路を通した。

| 確認 | 結果 |
|---|---|
| 未設定時 | 「verification mail not sent: set spring.mail.host and app.mail-from…」を記録し、登録は201で成功 |
| 未設定時のトークン漏れ | ログに**含まれない** |
| 確認メール | 受信。本文の確認コードがDBのトークンと**完全一致** |
| 再設定メール | 受信。本文の再設定コードがDBのトークンと**完全一致** |

### 途中で見つけたもの（未修正）

未確認アカウントで `POST /api/users/me/image` にファイルを付けずに投げると **500** が返る。
必須パートの欠落は400が妥当で、500は返すべきでない。今回の変更とは別件のため手を付けていない。

なお、curlから日本語のユーザー名で登録すると400になるのは、シェルの文字コードの問題で
アプリの不具合ではない。ASCII名では201で成功する。
