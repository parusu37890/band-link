# NFT（Playwright MCP対象外・非機能）— 2026-09-15 NFT-004/005/006/013

`docs/test-plan/test-cases.md`のNFT-004、NFT-005、NFT-006、NFT-013を実施した。2026-09-14までのバッチ（PW-A〜I、`docs/test-results/2026-09-14-st-playwright-pw*.md`）とNFT-003（コミット`9873c36`・`60622cc`、同時実行DB制約系の最初のケース）の続き。この4ケースはPlaywright MCP対象外（ブラウザ操作を伴わない、実DB・実APIへの直接検証）のため、ブラウザは使用していない。

副次修正として、PW-HのSEC-002で見つかっていた`/support`ページの案内文言と`EmailVerificationGateFilter`の実際の挙動の不整合（同記録の20行目に記載）も本セッションで解消した。

- 本セッション開始時点でDBはすでに84 users/74 postsへ再投入済みだった（前セッションの状態を引き継いだ）。
- `DatabaseConstraintInitializer`が新規に作る`post_images`用トリガー・関数（NFT-004の修正、下記）は、通常はアプリ起動時に自動適用されるが、本セッションでは同一マシン上の**別worktreeの別エージェントがすでにポート8080でアプリを起動しており**（`C:\Users\parus\Desktop\band\.claude\worktrees\agent-afce16a29dd9fc1e0`、プロセス確認済み）、ポート競合でこのセッション自身のアプリを起動できなかった。そのため、当該トリガーSQLを直接`psql`で適用して同じスキーマ状態を再現した(結合テストは`spring.jpa.hibernate.ddl-auto=none`で実行するため、いずれにせよ一度スキーマへ適用しておく必要がある)。CI(`ci.yml`)では引き続き「アプリを一度起動してスキーマを適用」という既存の手順がこのトリガーも自動的に作成する。他エージェントのプロセスやDBの他テーブルには一切触れていない。
- 破壊的なテスト（会話・画像行の一時削除やユーザー登録・ブロック行の作成）はすべて各テストの`@BeforeEach`/`@AfterEach`でJdbcTemplateにより実データを復元しており、セッション終了時点のDBは84 users/74 posts/1 block/4 conversationsで開始時と一致する。NFT-006自体で3回再投入も実施済み。

## 発見した不具合（修正済み）

### 1. 同時画像追加で5枚上限を超えうる（`PostImageService`、コミット後述）

- 修正前: `PostImageService.add()`/`addAll()`は`images.countByPostId(postId) >= 5`をチェックしてから`images.save(...)`する構造で、NFT-003で修正した`PostService.create/reopen`とまったく同じcheck-then-insertの非atomic性を持っていた。2つの同時リクエストが両方ともチェックを通過してから片方ずつcommitすれば6枚以上になりうる。加えて、`storage.store(file)`（実ファイル書き込み）が先に実行されるため、後からDB側で拒否されると書き込み済みファイルがorphanとして残る危険もあった
- 再現: U14の投稿P009（`920009`）の画像を5枚→4枚（1枚を一時的に削除、テストの`@BeforeEach`で行い`@AfterEach`で復元）にしたうえで、2つの画像追加リクエスト（`POST /api/posts/920009/images`）をCyclicBarrierで完全同時発火。修正前の状態を想定した検証は行わず（NFT-003の教訓を踏まえ、DB制約なしでの再現は省略し直接DB制約を先に設計・適用した）、DB制約適用後の実測で1件201・1件409・最終件数5・orphanファイル0を確認（下記「検証」参照）
- 修正: `count(*) <= 5`という集合的な制約は単純なUNIQUE/CHECKでは表現できないため、`post_images`へのBEFORE INSERTトリガー（`enforce_post_images_limit()`、`DatabaseConstraintInitializer`に追加）を新設。トリガーは親`posts`行を`FOR UPDATE`でロックしてから同一`post_id`の既存行数を数え、5件以上なら`RAISE EXCEPTION ... USING ERRCODE='23514'`で拒否する。`FOR UPDATE`ロックにより同一`post_id`への同時INSERTがトリガー内で直列化される。`PostImageService.add()`/`addAll()`のアプリ側チェックは高速パスとして残しつつ、`saveAndFlush`＋`DataIntegrityViolationException`捕捉で、(a) 敗者に対して既存の「募集画像は5枚までです」と同じメッセージ・409を返し、(b) 敗者がすでに書き込んでいたファイルを`storage.delete(url)`で削除してorphanを防ぐよう変更した
- 検証: 実際に2並列アップロードを発火し、レスポンス（201×1、409×1、5xx×0）、DB件数（5固定）、`uploads/`直下のファイル差分（新規ファイルは成功した1件の画像URLのみ）を照合。同一手順を複数回繰り返しても再現性があることを確認（2回連続実行でともにPASS）
- 回帰テスト: `PostImageConcurrencyIntegrationTest.nft004_concurrentUploadsNeverExceedFiveImagesAndLeaveNoOrphanFile`（実DB・実ファイルシステムに対する結合テスト、`QA_RELEASE_IT=true`必須）

### 2. 同時初回DMで会話一意制約エラーを利用者へ露出しうる（`MessageService`、コミット後述）

- 修正前: `MessageService.conversation()`は`conversations.findByUserAIdAndUserBId(...).orElseGet(() -> conversations.save(...))`という構造で、これも同じcheck-then-insertの競合を持っていた。`conversations`テーブルには元々`uk_conversation_pair`（`user_a_id, user_b_id`のUNIQUE制約、Hibernateのentity定義由来）が存在していたため「重複した会話が2件できる」ことはなかったが、敗者側は未捕捉の`DataIntegrityViolationException`をそのまま投げていた。PostgreSQLは1つの文がエラーになるとトランザクション全体がabortされる仕様のため、これをその場でcatchしても同一トランザクション内で`Message`の保存を続けることはできず、何もしなければ敗者のメッセージ送信リクエストが未処理のまま生の500になる構造だった（NFT-005が要求する「message2、5xx0」を満たせない）
- 再現: seedで用意されていたU07/U08の既存会話（C001、`930001`）を一時的に削除（メッセージ・通知含む、テストの`@BeforeEach`で行い`@AfterEach`で完全復元）して真の「初回DM」状態を作り、U07→U08とU08→U07の2つの送信リクエスト（`POST /api/messages`）をCyclicBarrierで完全同時発火
- 修正: 会話の新規作成部分だけを`TransactionTemplate`（`PROPAGATION_REQUIRES_NEW`）で独立したネスト転送に切り出した。ネスト転送内で`saveAndFlush`が一意制約違反で失敗しても、abortされるのはそのネスト転送だけで、呼び出し元の`send()`本体の転送（メッセージ・通知保存に使う）は無傷のまま再開できる。捕捉した`DataIntegrityViolationException`はその場で握りつぶさず、同じ(user_a_id, user_b_id)を再検索して、対抗リクエストがすでにcommitした会話行を取得し、そのままメッセージ送信を継続する。ユニットテスト用の6引数コンストラクタ（`TransactionTemplate`なし）はこれまで通りモックで動作するよう、`newConversationTx == null`のときは単純な`save()`にフォールバックする分岐を残した
- 検証: 2並列送信を発火し、レスポンス（200×2、5xx×0）、DB（会話1件のみ・メッセージ2件・すべて同一会話ID）を照合。実際に敗者側の接続で`SQLState 23505`（`uk_conversation_pair`違反）が発生しつつ、そのリクエスト自体は200で完了することをアプリログで確認した。3回連続実行してもすべてPASS、DBは毎回元の状態（C001・メッセージ3件・通知2件）へ正確に復元されることを確認
- 回帰テスト: `MessageConversationConcurrencyIntegrationTest.nft005_concurrentFirstDmProducesExactlyOneConversationAndTwoMessagesWithNo5xx`（実DBに対する結合テスト、`QA_RELEASE_IT=true`必須）

### 3. DB制約違反がアプリ経由で生の500になりうる汎用的なギャップ（`ApiExceptionHandler`、コミット後述）

- 発見の経緯: NFT-013の「アプリ経由の違反は4xxで500非公開」を確認する過程で、`ApiExceptionHandler`に`DataIntegrityViolationException`向けの汎用ハンドラが存在しないことに気付いた。`AuthService.register()`（`existsByEmail`→`save`のcheck-then-insert）と`BlockService.block()`（`existsByBlockerIdAndBlockedId`→`save`の同型）は、単発リクエストでは業務ロジック側の事前チェックで守られているが、同時実行レースで両方が事前チェックを通過した場合、敗者側は未捕捉の制約違反をそのまま投げ、ハンドラが無いため既定のSpring Boot 500になることを実測で確認した（同一メールでの同時新規登録、同一pairへの同時ブロックをそれぞれ実際に競合させて確認、下記「検証」参照）
- 修正: `ApiExceptionHandler`に`@ExceptionHandler(DataIntegrityViolationException.class)`を追加し、409 `DATA_CONFLICT`（汎用の安全なメッセージ、SQL詳細やconstraint名は含めない）を返すようにした。NFT-003/004/005で個別に対応した3件（`PostService`・`PostImageService`・`MessageService`）はそれぞれ専用の分かりやすいメッセージ・復旧ロジックを持つため変更していない。本ハンドラは、それら以外の——今回見つけた登録・ブロックの2件を含む——あらゆる制約違反に対する最終防衛線として機能する
- 検証: 修正後、同一メール同時登録は「1件201・1件409・users行数+1」、同一pair同時ブロックは「5xx0・blocksは重複せず1行」になることを確認。DB直結の6違反（下記）はいずれもアプリ層を経由しないため本ハンドラの対象外だが、修正前後でDB自体の拒否結果に変化はない
- 回帰テスト: `DatabaseConstraintDefenseIntegrationTest.nft013b_concurrentDuplicateRegistrationNeverSurfacesA500`、`.nft013b_concurrentDuplicateBlockNeverSurfacesA500AndStaysIdempotent`

## NFT-006 検証詳細（コード修正なし）

`scripts/test/seed-release-users.sql`を同一`qa_password_hash`で3回連続実行し、各回の直後に以下を測定した。

- 21テーブルの行数（users, posts, post_images, post_parts, post_genres, post_stances, post_prefectures, post_age_ranges, user_parts, user_genres, user_stances, user_prefectures, conversations, messages, notifications, blocks, reports, feedback, email_verification_tokens, password_reset_tokens, line_accounts）
- users/posts/conversations/messagesそれぞれの決定的checksum（`md5(string_agg(id::text||':'||...列, ',' order by id))`）
- conversations/blocksの重複pair件数、usersの重複email件数

3回すべてで**全項目が完全一致**した：users=84、posts=74（要求どおり）、post_images=5、conversations=4、messages=6、blocks=1、以下略。`users_checksum`は3回とも`eceadb0b5a1c7b53079208826eeacd7c`、`posts_checksum`は3回とも`54315c5098a55bed670fd67e22a0eb54`、`conversations_checksum`・`messages_checksum`も同様に3回とも完全一致。重複pair・重複emailはいずれの回も0件。`TRUNCATE ... RESTART IDENTITY`後にすべての行を固定ID（`910000+n`等）で再投入する既存の設計により、再投入は素朴に冪等であることを実測で確認した——スクリプト自体の修正は不要と判断した。

## NFT-013 検証詳細

### Part A: DB直結（各違反を個別トランザクションでINSERTし、SQLSTATE確認後にrollback）

| 違反 | SQL/対象 | 期待SQLSTATE | 結果 |

いずれもロールバック後に対象テーブルの行数が試行前と完全一致することを確認済み（既存行への影響なし）。

### Part B: API経由（4xxで500非公開の確認）

- 既存メールでの登録（`POST /api/auth/register`）: 単発リクエストで409（構造化エラーボディ、`exception`等の内部情報を含まない）、users行数は変化なし
- 同一メールでの**同時**登録（barrier同期の2並列）: 1件201・1件409、5xx0、users行数はちょうど+1（上記「発見した不具合」3.のとおり、修正前はここが500になりうる構造だった）
- 同一pairへの**同時**ブロック（barrier同期の2並列、U07→U11）: 5xx0、最終的にblocksへの重複なく1行のみ（修正前はここも500になりうる構造だった）

`conversations`の重複pair・`post_images`の5枚超はNFT-004/005自体がAPI経由の同時実行として既に検証済みのため、本ケースでの重複実施は行っていない。

## 副次修正: `/support`の案内文言と実際の挙動の不整合
